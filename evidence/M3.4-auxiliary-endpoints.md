## Acceptance mapping

### Every M0.2-observed endpoint has compatibility coverage

| Observed endpoint | Transport | Compatibility evidence |
|---|---|---|
| `/backend-api/codex/responses` | WebSocket | `proxy-routes.test.mjs`, `websocket-tunnel.test.mjs`, and `websocket-failover.test.mjs` cover exact route/upgrade behavior, bytes, cancellation, and semantic replay boundaries. |
| `/backend-api/codex/models?client_version=...` | HTTP JSON | `auxiliary-endpoints.test.mjs` covers exact method/path/query, empty request, safe headers, bounded JSON response, response-header filtering, and lease release. |
| `/backend-api/codex/alpha/search` | HTTP JSON | `auxiliary-endpoints.test.mjs` covers exact method/path, original JSON bytes, observed stable field types, safe headers, bounded JSON response, and lease release. |

The auxiliary policy test reads `evidence/M0.2-protocol-redacted.jsonl` directly and asserts both
observed HTTP requests and their paired `200 application/json` responses before comparing the
production policy.

### Request and response compatibility

- Models accepts only an empty request body and preserves the bounded `client_version` query.
- Search accepts UTF-8 `application/json` with the observed stable top-level types: string `id`,
  array `input`, finite numeric `max_output_tokens`, and string `model`.
- Unknown/dynamic search fields are not guessed or rewritten; validated requests reach the upstream
  as identical bytes.
- Auxiliary bodies are buffered within the configured request/response limits. Chunked overflow
  fails with `413` before account resolution.
- A successful auxiliary response is not committed until its content type and complete JSON body
  validate. Invalid or oversized output becomes a bounded `502` without forwarding its canary body.
- The same models/search success path is tested with M3.3 failover mode enabled and one fixture
  account. No second selection or account switch occurs.

### Header and secret boundary

- Each auxiliary route forwards only M0.2-observed client-safe headers. Host and content length are
  regenerated by the proxy.
- `authorization` and `chatgpt-account-id` can only come from the internal resolver. Client
  authorization, account IDs, cookies, API keys, and Responses-only session/turn headers are
  stripped.
- Upstream `set-cookie` and private headers are stripped. The observed safe `etag` and
  `x-oai-request-id` response headers are preserved.

### Unsupported endpoints fail closed

- Unknown suffixes and the unobserved memory path return structured `404 route_not_allowed` before
  the resolver is called.
- Wrong methods return structured `405 method_not_allowed` plus a bounded `Allow` header.
- Search queries return structured `400 query_not_allowed`.
- An HTTP request to the observed Responses WebSocket path returns structured
  `426 websocket_required`.
- Route error bodies contain only `error`, numeric `status_code`, and bounded `allowed_methods`; the
  rejected target is never echoed.

## Residual risks

- M0.2 was captured from Codex CLI 0.144.2. Future runtime changes to the stable search fields or
  safe header vocabulary require a new authorized shape capture and compatibility update.
- M0.2 intentionally redacted dynamic field names and all values. M3.4 preserves unknown fields but
  cannot claim semantic knowledge of them.
- Exact non-2xx auxiliary error-body compatibility was not observed. Such responses remain bounded
  and header-filtered; M3.3 handles explicit retryable status classes when failover is enabled.
- The separate `/v1/models` compatibility route predates M3.4 and was not observed in the Codex
  0.144.2 capture; M3.4 makes no M0.2 claim for it.
- Real Codex App Server E2E, including approved account-switch and historical thread scenarios,
  remains M3.5. No mock result substitutes for that gate.
- No memory endpoint is supported unless a later authorized protocol capture observes one.
- No seamless cross-account conversation-continuity claim is permitted.
