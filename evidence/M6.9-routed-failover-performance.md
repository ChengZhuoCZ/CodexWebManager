# M6.9 routed codex-web failover and performance

## Result

M6.9 completed the clean-room failover implementation, fixture qualification,
single-account live path, and isolated 8216 deployment work through release
r18. Release r15 disabled authenticated Statsig event collection after the
public Statsig implementation was used to explain page-side event-drop
warnings. Release r16 moves the already-versioned main-module resource hint
ahead of the synchronous Tailnet startup shim so a cold multi-megabyte
transfer no longer waits for that shim's Tailnet round trip. Release r17
hash-pins and inlines the 1,942-byte shim at the same execution position, so
the HTML parser no longer performs its separate revalidation request. Release
r18 adds deterministic Brotli and gzip siblings for the final HTML without
changing its identity bytes.

The r17 change modifies only deterministic `index.html` delivery. It preserves
script execution order, the main asset URL and bytes, account selection, model
requests, App Server IPC, network routes, and the independent 8215 deployment.
The live page retained a signed-in composer, completed two fixed non-private
single-account model sentinels, and produced zero
Statsig/manual-flush/event-drop warnings and zero page error logs.

End-to-end browser startup remained variable, so no stable startup-speed or
response-latency guarantee is claimed. The task also remains blocked at the
real two-account gate because the server has one configured, enabled, usable
credential. No real A-to-B switch was attempted, and no seamless
cross-account continuity or in-flight computation-resume claim is made.

Public mature-project behavior was used only as design input:
[`0xcaff/codex-web`](https://github.com/0xcaff/codex-web) informed the
long-lived App Server/thin-wrapper boundary,
[`codex app-server`](https://github.com/openai/codex/blob/main/codex-rs/app-server/README.md)
defined the connection lifecycle,
[`@fastify/static`](https://github.com/fastify/fastify-static) supplied the
existing precompressed-file path, and
[`statsig-io/js-client-monorepo`](https://github.com/statsig-io/js-client-monorepo)
was inspected to distinguish disabled event collection from a failed network
override. All integration code remains a small clean-room adapter; no
implementation was copied.

## Automatic failover integration

The routed App Server remains fixed to the loopback account-router model
origin. The complete HTTP/SSE and WebSocket fixture matrix covers quota, 429,
authentication, network, upstream-5xx, malformed pre-semantic SSE, and
post-semantic refusal. Attempts, backoff, and the whole-pool deadline are
bounded. A request is never replayed after semantic SSE or WebSocket output.

The installed `codex-router-account enroll` workflow accepts only a private
regular Codex auth file path, validates it before changing state, uses a
private lock and atomic file operations, installs a root-owned mode `0600`
systemd credential, updates only the public account catalog, restarts only the
account router, requires all configured accounts to become usable, and rolls
back on failure. Its output contains only bounded counts and never a token,
email, provider account identifier, or full quota response.

The server still exposes one configured account in the browser status panel.
The enrollment command was not invoked because no second authorized private
credential was staged.

### r16 resource-discovery experiment

Before r16, the HTML parser encountered the synchronous
`tailnet-startup-fastpath.js` request before the main-module preload. From the
Mac over Tailnet:

- HTML TTFB was 329.478-331.802 ms and total time was 497.809-500.189 ms;
- the 1,942-byte synchronous shim TTFB was 330.307-332.061 ms and total time
  was 330.499-332.133 ms;
- main-module TTFB was 331.412-335.984 ms, while its three transfer totals
  varied at 2.216, 8.671, and 2.375 seconds.

This establishes a deterministic avoidable dependency: discovery of the cold
main transfer waited behind roughly one 330 ms Tailnet round trip. The r16
builder fails closed unless it can relocate exactly one versioned main-module
hint next to the import map and ahead of the synchronous shim. It does not
move or defer either script.

The live r16 DOM confirmed one import map and one main preload with head child
indices 2 and 3, followed by the startup shim and preload module at indices 4
and 5. The mapped and preloaded URL remained identical to r15, so existing
immutable caches were preserved instead of forcing a multi-megabyte
redownload.

Three cached r16 navigations reached the signed-in composer in bounded
observations of 7,118, 8,104, and 10,452 ms. These remain within the broad
historical variance and do not prove a stable end-to-end improvement. The
removed cold discovery dependency is deterministic; its actual wall-clock
benefit still depends on cache state, connection scheduling, transfer, parse,
and renderer work.

One fixed non-private model sentinel completed in 6,842 ms under 500 ms
polling. That is an observation, not a latency guarantee, and no prompt or
response body was retained in repository or server evidence.

### r17 synchronous-shim request experiment

The r16 HTML still contained a synchronous external
`tailnet-startup-fastpath.js` element. Its route used
`Cache-Control: public, max-age=0`, so even a cached browser revalidated the
1,942-byte file across the Tailnet. The earlier direct probes measured that
request at 330.499-332.133 ms total. Adding its fixed source to the 15.6 KB
HTML costs 1,947 index bytes but removes that request from the parser's
blocking dependency.

Test-first evidence changed the expected external script to one inline marker;
the focused test failed against r16 behavior and passed after implementation.
The adapter also rejects a wrong index or script hash, unsafe closing-script
source, wrong resource order, and a second application to an already-inlined
index while leaving the last valid file intact.

The live r17 DOM contained one inline marker and zero external startup-shim
script elements. It retained one import map, one matching versioned main hint,
the unchanged preload module, the signed-in composer, and no alert surface.
Two same-tab cached navigations reached the composer in 14,330 and 18,845 ms;
a separate first-tab observation was only an upper bound of 24,593 ms because
browser-control scheduling occurred between navigation and the readiness
poll. These observations are slower and more variable than the r16 samples,
so they do not demonstrate a stable end-to-end speedup. The eliminated
external request is deterministic; main transfer, parse, and renderer work
still dominate the variable remainder.

Two fixed non-private single-account model sentinels completed. One timing run
completed in 8,917 ms under 250 ms polling. This is an observation, not a
guarantee. No prompt or response body was written to repository evidence or
server logs, and no account switch was requested.

## Telemetry experiment

Page diagnostics on r14 showed genuine manual Statsig flush failures and 99
dropped events. Public Statsig source shows that
`preventAllNetworkTraffic` returns before `networkOverrideFunc`, and the event
sender represents the absent response as a failed status. The authenticated
Codex client options omitted the `loggingEnabled: "disabled"` setting already
present in its pre-login options.

The r15 patch disables collection at that authenticated client boundary. The
r17 page retained zero Statsig/manual-flush/event-drop warnings and zero error
logs after navigation and both model checks. Its only page console entry was
an existing React route warning.

Separate network errors carrying a Browser control plugin client key were
traced to the local Browser control plugin bundle, not to the served codex-web
bundle. They are excluded from page-performance evidence and were not used to
justify a codex-web network change.

## User-authorized standalone 8215 repair

The original M6.9 scope protected 8215 from changes. During r18 preparation the
user explicitly interrupted the task and authorized repair of 8215. Read-only
diagnosis reproduced a startup screen that eventually left an empty root while
HTTP and static resources remained 200. The old standalone release delivered a
22,822,156-byte uncompressed main module and had no Tailnet startup telemetry
or precompressed-file adapter.

The repair created immutable r2 and r3 successors and retained every previous
release for rollback. r2 added only the exact reviewed non-provider startup
and Statsig adapters. r3 used integrity-verified npm package
`@esbuild/linux-x64@0.27.0` to produce the same qualified 14,138,835-byte
identity main module, 3,294,106-byte Brotli body, and 4,345,031-byte gzip body
used by the routed build. No router UI, account configuration, credential, or
model endpoint was copied into the standalone release.

From the Mac over Tailnet, the standalone main-module transfer changed from a
45.491-second identity observation to 4.206 seconds with Brotli and 7.297
seconds with gzip. The signed-in composer rendered, and a post-boundary fixed
model sentinel completed in 3,728 ms. Browser startup still varied, so only the
payload and transfer observations are claimed.

The first r3 activation attempt correctly rolled back because its verifier did
not normalize CRLF response headers. The candidate body and Brotli decode were
valid. A corrected hash-pinned activation succeeded. The same test-first
logging rule already used by 8216 was then applied to the standalone systemd
unit: `StandardOutput=null`, `StandardError=journal`. After restart and a real
model sentinel, the bounded 8215 journal scan contained 10 rows, zero sensitive
shape matches, zero sentinel matches, and no new application error.
