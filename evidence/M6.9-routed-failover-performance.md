## Automatic failover integration

The routed App Server remains fixed to the loopback account-router model
origin. The complete HTTP/SSE and WebSocket fixture matrix covers quota, 429,
authentication, network, upstream-5xx, malformed pre-semantic SSE, and
post-semantic refusal.

The installed `codex-router-account enroll` workflow accepts only a private
regular Codex auth file path, validates it before changing state, uses a
private lock and atomic file operations, installs a root-owned mode `0600`
systemd credential, updates only the public account catalog, restarts only the
account router, requires all configured accounts to become usable, and rolls
back on failure. Its output contains only bounded counts and never a token,
email, or provider account identifier.

The server still exposes one configured account in the browser status panel.
The enrollment command was not invoked because no second authorized private
credential was staged.

## Startup and response-path performance

The exact post-integration 22,822,120-byte main input remains pinned by
SHA-256. The reproducible builder pins esbuild `0.27.0`, syntax-checks the
smaller ESM result, and deterministically generates gzip and Brotli variants.
The deployed main identity is 14,138,809 bytes; gzip is 4,345,029 bytes;
Brotli is 3,293,232 bytes. All three decode to identity SHA-256
`3376a894219534630a550a314f4e64f1fa3e85cd12e76d32d0fdb7381c2645a9`.

Release r14 additionally pins and verifies the 607,155-byte preload input,
minifies it to 253,451 bytes, and emits 79,865-byte gzip and 69,315-byte
Brotli variants. It preserves the 79,327-byte initial stylesheet and emits
14,921-byte gzip and 13,143-byte Brotli variants. Every compressed sibling was
decoded and matched to its identity SHA-256 before activation.

The minimum experiment and implementation:

- pin and verify the unmodified candidate `index.html` SHA-256 before build;
- reject a changed layout, an existing import map, or an already-versioned
  candidate;
- insert exactly one import map before the earliest module script;
- map the normalized main asset specifier to
  `./assets/app-initial-BTphDPeq.js?v=3376a89421953463`;
- update the matching `modulepreload` to the identical URL;
- delegate encoding selection and validators to upstream's existing
  `@fastify/static` plugin rather than a custom response implementation;
- normalize `.br` and `.gz` siblings to their identity path before applying
  the existing cache policy;
- emit `Vary: Accept-Encoding`, preserve immutable caching for hashed main/CSS
  assets, and preserve revalidation for un-hashed preload;
- verify Brotli, gzip, identity, q-values, content types, range support, and a
  Brotli ETag conditional 304.

The candidate index SHA-256 is
`1ea73bdcd7a5ef303e9435796b58dc2cb66ba7916084c0afe7c9c1b8851c13fc`.
Remote offline verification matched every local hash before activation. The
active browser then showed one import map, an identical mapped/preload URL, a
usable composer, and a successful fixed non-private single-account model
sentinel. Prompt and response bodies were not retained.

From the Mac over Tailnet, three r14 main Brotli transfers completed in
2.208-2.277 seconds. The formerly uncompressed 607 KB preload had taken about
1.257-1.265 seconds; its 69 KB Brotli form completed in 0.667-0.668 seconds,
about 47% faster. The 13 KB stylesheet Brotli form completed in
0.494-0.501 seconds.

The browser still observed a usable composer at 5,452 ms, 9,841 ms, and
7,548 ms. Two minimal single-account requests completed; the second was
present at a bounded post-check upper bound of 25,813 ms after the exact
locator wait timed out. Failed best-effort Statsig requests were also visible
in the browser diagnostics. These observations are recorded as residual
client/session/network variance: r14 materially reduces static transfer but is
not claimed to guarantee stable end-to-end startup or model latency.
