# M6.9 routed codex-web failover and performance

## Result

M6.9 completed the clean-room implementation, fixture qualification,
single-account live path, and isolated 8216 deployment work. Release r15 adds
one authenticated-client Statsig option, `loggingEnabled: "disabled"`, after
the existing options were inspected and the public Statsig implementation was
used to explain the observed event-drop warnings. It does not change account
selection, model requests, App Server IPC, network routing, or the independent
8215 deployment.

The live r15 browser no longer produced manual-flush, `log_event_failed`, or
Statsig event-drop warnings. A fixed non-private single-account model sentinel
completed. Cold and cached usable-screen observations remained variable, so
no stable startup-speed or response-latency improvement is claimed.

The task remains blocked at the real two-account gate because the server has
one configured, enabled, usable credential. No real A-to-B switch was
attempted, and no seamless cross-account continuity or in-flight
computation-resume claim is made.

Public mature-project behavior was used only as design input:
[`0xcaff/codex-web`](https://github.com/0xcaff/codex-web) informed the
long-lived App Server/thin-wrapper boundary,
[`@fastify/static`](https://github.com/fastify/fastify-static) supplied the
existing precompressed-file path, and
[`statsig-io/js-client-monorepo`](https://github.com/statsig-io/js-client-monorepo)
was inspected to distinguish disabled event collection from a failed network
override. All integration code remains a small clean-room adapter; no
implementation was copied.

## Automatic failover integration

The routed App Server remains fixed to the loopback account-router model
origin. The complete HTTP/SSE and WebSocket fixture matrix covers quota, 429,
authentication, network, upstream-5xx, malformed pre-semantic SSE, and
post-semantic refusal. Attempts, backoff, and the whole-pool deadline are
bounded. A request is never replayed after semantic SSE or WebSocket output.

The installed `codex-router-account enroll` workflow accepts only a private
regular Codex auth file path, validates it before changing state, uses a
private lock and atomic file operations, installs a root-owned mode `0600`
systemd credential, updates only the public account catalog, restarts only the
account router, requires all configured accounts to become usable, and rolls
back on failure. Its output contains only bounded counts and never a token,
email, provider account identifier, or full quota response.

The server still exposes one configured account in the browser status panel.
The enrollment command was not invoked because no second authorized private
credential was staged.

## Startup and response-path performance

The r15 source was reproduced from pinned upstream revision
`c3e92f0fc16d...` by applying the existing small integration patches followed
by `tailnet-statsig-logging-disabled.patch`. A real unified-patch dry-run and
application succeeded. The only line added by the r15 patch is the
authenticated Statsig option `loggingEnabled: "disabled"`.

The reproducible builder pins esbuild `0.27.0`. The 22,822,156-byte main input
was minified to 14,138,835 bytes, with 4,345,031-byte gzip and
3,294,106-byte Brotli siblings. Identity, decoded gzip, and decoded Brotli all
matched SHA-256
`5d211964500013a9c68eb546775cb6cb071b080591881109239fec10bebbc7e0`.
The output-hash URL is
`./assets/app-initial-BTphDPeq.js?v=5d211964500013a9`.

The unchanged preload is 253,451 bytes identity, 79,865 bytes gzip, and
69,315 bytes Brotli. The unchanged initial stylesheet is 79,327 bytes
identity, 14,921 bytes gzip, and 13,143 bytes Brotli. The output index SHA-256
is `89fe33825e43f5de90525c0da05e9d51bef94df27a5667aa3d244d15b2a9fa36`.
All inputs, outputs, and compressed decodes were hash-checked before
activation.

The long-lived App Server Unix-socket probe showed:

- initialize: 15.8 ms;
- first round: account/read 1.7 ms, model/list 1.7 ms, thread/list 23.2 ms,
  config/read 2.4 ms;
- second round: account/read 1.5 ms, model/list 1.5 ms, thread/list 6.7 ms,
  config/read 1.9 ms.

The probe printed only method, status, timing, and count. It retained no
account, model, thread, prompt, or response body. These measurements rule out
App Server initialization RPC as the source of the remaining multi-second
startup. Large-bundle transfer, parsing, and renderer boot are the remaining
likely contributors; that attribution is an inference, not a proved causal
breakdown.

The r15 browser showed one import map, an identical mapped/preload URL, a
signed-in composer, and a completed fixed non-private model sentinel. The
first cold usable-screen upper bound was 10,132 ms. One cached navigation
reached the composer at 6,590 ms after a 439 ms navigation. These results are
within the broad r14 variance of 5,452/9,841/7,548 ms, so r15 is not claimed
to provide a stable end-to-end speedup. Precise model latency is also not
claimed because the final observation included browser-tool polling delay.

The r15 Brotli main response was 3,294,106 bytes and the gzip response was
4,345,031 bytes. Both returned HTTP 200 with the expected content encoding,
JavaScript content type, `Vary: Accept-Encoding`, and immutable cache policy.
The static-serving implementation was unchanged from r14, whose complete
Brotli/gzip/identity, q-value, range, ETag, and conditional-304 matrix remains
applicable.

## Telemetry experiment

Page diagnostics on r14 showed genuine manual Statsig flush failures and 99
dropped events. Public Statsig source shows that
`preventAllNetworkTraffic` returns before `networkOverrideFunc`, and the event
sender represents the absent response as a failed status. The authenticated
Codex client options omitted the `loggingEnabled: "disabled"` setting that was
already present in its pre-login options.

The r15 patch disables collection at that authenticated client boundary.
After the model check, the page had zero Statsig/manual-flush/event-drop
warnings and zero error logs; the only retained console entry was an existing
React route warning.

Separate network errors carrying a Browser control plugin client key were
traced to the local Browser control plugin bundle, not to the served codex-web
bundle. They are excluded from page-performance evidence and were not used to
justify a codex-web network change.

## Log boundary

The routed unit discards compatibility standard output and retains only
standard error in the journal. From r15 activation through the live model
check, 17 bounded journal lines were present with:

- zero syntax, chunk-load, or unhandled-error matches;
- zero authorization, cookie, bearer, email, prompt-sentinel, or other
  sensitive-shape matches;
- one systemd priority entry emitted by `nologin`.

The `nologin` entry has the same bounded hash as 13 entries observed before
r15 activation and does not match syntax, module, address, request, or Statsig
categories. It is therefore recorded as a pre-existing host event, not a new
r15 application error. Historical records created before the current log
boundary remain a retention/access risk and must be handled through the
server's journal policy.
