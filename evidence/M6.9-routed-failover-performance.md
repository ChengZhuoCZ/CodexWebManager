## Automatic failover integration

The routed App Server remains fixed to the loopback account-router model
origin. Existing HTTP/SSE and WebSocket state machines passed the complete
quota, 429, authentication, network, upstream-5xx, malformed-pre-semantic-SSE,
and post-semantic refusal matrix.

The new `codex-router-account enroll` command makes a second private binding
operationally safe:

- accepts an absolute path to a private regular Codex auth file, never a token
  value on the command line;
- validates the credential structure before changing service state;
- rejects identifying aliases and duplicate public bindings;
- uses a private concurrency lock and atomic file operations;
- installs a root-owned mode `0600` systemd credential;
- atomically updates the public account catalog;
- restarts only `codex-account-router.service`;
- requires every configured account to become usable;
- restores both files and the previous router process if restart/readiness
  fails;
- emits only a bounded result with account count and
  `credentials_exposed=false`.

The server currently reports one configured, enabled, usable account and one
matching private account credential. The command is installed and its help
probe succeeds, but it was not invoked with a second real credential.

## Startup and response-path performance

The r9 release served a 22,822,120-byte patched desktop bundle as a
5,116,196-byte gzip file or a 3,739,265-byte Brotli file. Release r10 adds a
reviewed, reproducible final-asset build step:

- the exact post-integration input is pinned by SHA-256;
- esbuild is pinned to `0.27.0` with fixed Chrome 120 ESM arguments;
- minification runs only after the compatibility and IPC patches;
- Node syntax-checks the result before activation;
- gzip and Brotli outputs are deterministic and decode to the same identity;
- an inactive release is validated before changing the `current` symlink.

The test-first minimum experiment initially failed because the builder module
did not exist. Its first implementation then exposed that Node cannot syntax
check a temporary file ending in `.next`; changing the temporary suffix to
`.next.js` made all seven focused fast-path tests pass before deployment.

The deployed identity is 14,138,809 bytes, 38.0% smaller than r9. Its gzip
body is 4,345,029 bytes and its Brotli body is 3,293,232 bytes, respectively
15.1% and 11.9% smaller than r9. The served identity SHA-256 is
`3376a894219534630a550a314f4e64f1fa3e85cd12e76d32d0fdb7381c2645a9`.
The live server prefers `br`, falls back to `gzip`, preserves identity
responses, emits `Vary: Accept-Encoding`, and retains immutable caching.

The connection-reuse experiment proved two sequential routed requests already
share one completed upstream HTTP connection, so no speculative proxy change
was made.

The recorded r9 cold entry required 6,531 ms to reach a usable composer. After
the r10 process was actually restarted and the served body hash was verified,
three browser entries reached the usable composer in 4,280 ms, 1,861 ms, and
2,002 ms. The first r10 observation is 34.5% below the recorded r9 cold entry;
the later observations show the warm-cache path. These are deployment
observations, not a general benchmark.

One fixed non-private single-account browser sentinel completed through the
actually restarted r10 process. The DOM showed one user-prompt occurrence and
two bounded expected-token occurrences, with no visible request, login,
syntax, or chunk-load error. Prompt and response bodies were not stored in
repository evidence.

Because upstream content-hashed the filename before the clean-room integration
changed the bytes, a browser that cached r9 with `immutable` may need one normal
reload before receiving r10. Renaming every linked chunk would be a larger and
riskier upstream rewrite, so this rollout limitation is recorded explicitly.

## Log boundary correction

The earlier live model check revealed that the upstream Electron compatibility stub
printed complete IPC messages and upstream response headers to standard
output. The routed unit now sets `StandardOutput=null` while retaining
`StandardError=journal`. The final r10 model sentinel produced zero routed
service journal lines, zero sentinel matches, zero Electron IPC matches, and
zero authorization, cookie, account, body, access-token, or refresh-token
pattern matches.

Historical journal records created before this boundary cannot be deleted by
unit without vacuuming unrelated system logs. They remain a retention/access
risk and must be handled by the server's journal retention policy.
