## Protocol boundary

The implementation follows the public Codex rate-limit shapes rather than copying another
manager implementation. The OpenAI Codex App Server documentation defines rate-limit reads and
updates with used percentage, window duration, and reset time. The upstream Codex rate-limit
parser documents `codex.rate_limits` with `primary` and `secondary` windows using
`used_percent`, `window_minutes`, and `reset_at`.

Sources:

- https://github.com/openai/codex/blob/main/codex-rs/app-server/README.md
- https://github.com/openai/codex/blob/main/codex-rs/codex-api/src/rate_limits.rs

M2.5 accepts one unambiguous 10079- or 10080-minute Codex window and converts it to a sanitized
weekly remaining ratio. Unknown limit buckets, invalid percentages, invalid resets, duplicate
weekly windows, unrelated events, and malformed SSE do not create a new observation. No credit
balance, raw rate-limit event, credential, account email, or authorization value enters the
runtime quota store or admin status.

## Delivered behavior

- HTTP SSE and WebSocket relays publish only a sanitized per-account weekly observation.
- Fresh weekly-only snapshots participate in deterministic scheduling even though the five-hour
  window is unsupported.
- An account with fresh weekly remaining ratio `0` is excluded before the next request.
- Admin status reports the sanitized weekly ratio and marks a fresh zero ratio as
  `quota_exhausted`.
- The existing semantic-output safety boundary is unchanged: no request is replayed to another
  account after semantic SSE output.
- Missing observations remain unavailable; stale observations fall back to the existing
  conservative unknown-quota tier.

## Verification

The failure-first run produced the expected five failures. After implementation, the focused
weekly quota suite passed 31/31. The complete local matrix passed 235/235 with no failures or
skips, including both pre-semantic and post-semantic failover boundaries. The repository security
audit scanned 274 files with no findings and passed 75/75 focused security tests. Exact commands
and summarized outputs are recorded in `evidence/M2.5/test-summary.json`.

All upstream servers, accounts, credentials, quota events, and UI scenarios were synthetic local
fixtures. No real account was configured and no account-switch scenario was executed.

## Residual risks

- Five-hour quota is not available from the selected observation path and remains `unavailable`;
  scheduling is currently based on fresh weekly quota only.
- Weekly observations are learned from account-specific model traffic after process start and are
  not persisted across a process restart.
- A real-account E2E is still required before claiming the deployed upstream emits the same
  weekly event shape for the user's accounts.
- Cross-account response-chain portability remains deferred. This task does not claim in-flight
  recovery, original-session preservation, or seamless continuity.
