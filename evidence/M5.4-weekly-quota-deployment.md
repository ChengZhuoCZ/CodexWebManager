M5.4 packages the completed M2.5 weekly quota runtime into a distinct immutable Linux x64 release
and deploys it through the checked M5.3 snapshot and rollback workflow. The target is an authorized
private Tailnet server. Only the already configured Primary account is used.

No second account is configured, no account switch is attempted, and no cross-account continuation,
in-place computation recovery, or seamless continuity claim is made. The user-directed 24-hour soak
exception remains in effect.

## Snapshot-backed upgrade

The release's checked-in deployment command upgraded the active router from 0.2.0 to 0.2.1. It
created private snapshot `20260728T053940720Z-bed713d062e5`, recorded the previous immutable release,
and reported `credentials_included: false`. The snapshot directory is mode 0700.

Post-upgrade checks confirmed:

- the active symlink and package version select 0.2.1;
- the weekly quota runtime file is present;
- router, App Server, and codex-web services are active;
- router health and readiness return HTTP 200;
- the App Server Unix socket exists;
- the one-account public configuration remains enabled;
- the account configuration and both credential slots remain mode 0600;
- the private Tailnet web health endpoint returns HTTP 200 from the client device.

Credential contents, account email, tokens, cookies, authorization headers, and raw upstream quota
responses were neither printed nor stored in this evidence.

## Bounded real single-account evidence

A 120-second, read-only, ephemeral Codex request was sent through the 0.2.1 loopback router. It used
only Primary, exited with code 0, matched the fixed expected response, and left router readiness at
HTTP 200.

The protected admin status was queried server-side with the token kept only in process memory and
then reduced to whitelisted fields. Primary remained healthy, the weekly remaining ratio was `1`,
and a weekly observation timestamp was present. Five-hour quota remained unavailable and
`last_switch_reason` remained null.

This confirms that the deployed single-account path can observe the currently available weekly
quota. It does not validate automatic account switching.

## Residual risks

- Only one real account is configured, so quota-exhaustion switching and cross-account behavior
  remain untested.
- Five-hour quota is unavailable, and weekly observations are not persisted across router restart.
- M6.2 remains rejected under the user-directed soak exception; this deployment is not a full
  production-release qualification.
- Direct Tailnet HTTP requires the codex-web login form and its separate site access key. The public
  health endpoint is reachable, while unauthenticated application requests are intentionally
  rejected.
