## Implemented boundaries

### Independent supervision

`codex-stack.target` wants all three services, while the services use only `Wants=` and `After=` for
availability and ordering. They deliberately omit `Requires=`, `BindsTo=`, `PartOf=`, and stop/reload
propagation. Restart policy is bounded by start-rate limits, nonzero backoff, and explicit stop
timeouts.

### Local-only transports

- router model: `127.0.0.1:18317`
- router admin: `127.0.0.1:18318`
- codex-web: `127.0.0.1:8214`
- App Server: `/run/codex-app-server/app-server.sock`

The wrapper accepts proxy mode only for the exact pinned codex-web invocation and an absolute,
normalized, bounded `.sock` path below `/run/`. Public WebSocket input, arbitrary options, control
characters, traversal, and non-runtime socket paths fail closed. M4.1 direct mode is unchanged when
the socket variable is absent.

### Credential delivery

The units use `LoadCredential=` and `ImportCredential=`. Public environment values contain only
loopback addresses, ports, executable paths, and `%d` credential paths. No credential value appears
in `ExecStart=` or `Environment=`. `ProtectSystem=strict` and explicit mount namespacing isolate the
per-service credential directories, consistent with the systemd
[credential model](https://systemd.io/CREDENTIALS/).

Native testing established that systemd 255 presents credential directories and files as
root-owned read-only mounts. The implementation therefore has a separate provider that accepts
that ownership model only when `CREDENTIALS_DIRECTORY` exactly equals one single-unit directory
under `/run/credentials/`. The ordinary file provider remains service-user-owned and mode `0700`
or `0600`; paths under `/etc`, another unit, or a nested directory cannot opt into systemd mode.
The optional codex-web status bridge applies the same boundary.

### Common sandbox

All services use the non-login `codex` identity, `UMask=0077`, empty capability sets,
`NoNewPrivileges=true`, private temporary/device/mount namespaces, strict host filesystem
protection, kernel/control-group/clock protection, SUID/SGID and personality restrictions, native
system-call architecture, and only Unix/IPv4/IPv6 address families. State and runtime directories
are mode `0700`.

`MemoryDenyWriteExecute=` is not enabled because the Node.js runtime uses a JIT. Namespace filters
that could silently break an authorized Codex tool sandbox are not guessed without a real protocol
experiment.

## Native Ubuntu evidence

The lifecycle verifier passed twice against the validated implementation: once on the
user-authorized Ubuntu 24.04 host and once in GitHub Actions run
[`30245335738`](https://github.com/ChengZhuoCZ/CodexWebManager/actions/runs/30245335738).
The GitHub run completed successfully in 18 seconds at commit `66fcc63`; its lifecycle job completed
in 13 seconds and uploaded `systemd-lifecycle-evidence`.

The first authorized-host attempt exposed root-owned systemd credential mounts, and the next
attempt exposed a trailing newline from the fixture token generator. Both failures were fail-closed
before a listener started. The final design uses the scoped provider described above and writes the
fixture bearer value without trailing whitespace.

The sanitized output is preserved in `evidence/M5.2/systemd-lifecycle.json`, with the Actions
metadata in `evidence/M5.2/github-actions-summary.json`. It proves:

1. systemd 255/PID 1 supervision with Node.js 22.23.1 and one shared non-root service UID;
2. literal `127.0.0.1` TCP listeners plus the App Server Unix socket, with no public listener;
3. systemd credential-file delivery and zero secret-like MainPID command-line matches;
4. an independent restart of every service, with each restarted PID changing and both peer PIDs
   remaining unchanged.

Both evidence documents explicitly record `real_account_configured:false`,
`account_switch_tested:false`, and `seamless_account_continuity_claimed:false`.
