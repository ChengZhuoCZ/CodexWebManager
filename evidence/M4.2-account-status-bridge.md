## Result

M4.2 adds an optional server-side status bridge without changing the normal Codex model or IPC
paths. With no router variables, the bridge performs no admin request and its two reserved routes
return `404 {"enabled":false}`. A fixture single-account route remained usable in this mode.

When both server variables are configured, codex-web may read sanitized router state from
`/__backend/codex-router/status` and sanitized `router.switch` SSE frames from
`/__backend/codex-router/events`. The browser never receives the admin token.

The codex-web change is a small overlay pinned to the exact upstream source revision and main-file
digest. Tests apply it only to a private temporary copy, compile it with the pinned upstream
TypeScript toolchain, and run a Fastify harness. The pinned upstream checkout remained tracked-clean.

## Security and privacy properties

- Admin origin accepts only `http://127.0.0.1:<port>` or `http://[::1]:<port>` with no path,
  credentials, query, or fragment.
- The admin token is read server-side from a service-user-owned private regular file in a private
  directory. Symlinks, group/other permissions, malformed values, and oversized files fail closed.
- Status is copied through an exact field whitelist. Injected internal IDs, credential bindings,
  authorization-like fields, tokens, and unknown quota fields do not pass.
- Events accept only bounded, valid `router.switch` SSE frames and are rewritten from sanitized
  values. Unknown event types, fields, malformed JSON, cursors, and oversized frames fail closed.
- Status reads have a total 3-second deadline and 64 KiB body limit. Event connection setup has a
  3-second deadline and individual pending frames are limited to 16 KiB.
- Browser responses are same-origin and carry `no-store` plus `nosniff` protections.

## Acceptance evidence

1. **codex-web receives only sanitized status/events**: the integration fixture deliberately adds
   `credential_ref`, authorization-like, token, and unknown fields; none appear in browser-facing
   JSON or SSE.
2. **Feature disabled when router is not configured**: the adapter starts without either router
   variable, returns explicit disabled 404s, and makes no router request.
3. **No standard single-account regression**: the pinned overlay compiles inside a temporary
   codex-web server tree; an unrelated fixture route remains `200` while both bridge routes remain
   disabled. The complete account-router suite passes 160/160.

## Residual risks

- The overlay is intentionally pinned. A later codex-web revision requires source review and a new
  digest rather than automatic fuzzy patching.
- JavaScript strings containing the bearer token cannot be forcibly zeroed; code confines the
  value to the server-side authorization callback and never logs or serializes it.
- The browser UI does not consume this bridge until M4.3.
- No account switch was executed. M4.2 is not cross-account continuity evidence, M0.3/M3.5/M4.1
  account-switch rows remain mandatory, and no seamless continuity claim is permitted.
