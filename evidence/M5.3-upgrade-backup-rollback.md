## Implemented boundaries

### Restart-persistent health

The router loads its circuit document from `CODEX_ROUTER_STATE_DIRECTORY` before composing the
runtime. Failure, half-open probe, recovery, and shutdown transitions are persisted atomically.
Persistence errors make readiness and later account selection fail closed rather than silently
forgetting health history.

On restart, cooldown timestamps and prior failures are restored, while in-flight probe leases are
intentionally discarded. This preserves account health history; it does not resume an active
request or calculation.

### Private backup and schema gate

The deployment manager validates the release manifest, archive digest, platform, architecture,
bounded payload, file modes, and declared configuration/state schema before activation. The pinned
0.1.0 baseline is documented as an implicit schema-1 release; 0.2.0 declares schema 1 explicitly.
Unknown or incompatible schemas fail before the current release symlink changes.

Every upgrade first writes a mode-0700 snapshot directory containing mode-0600 configuration and
circuit-state copies, checksums, original ownership/modes, and release metadata. Credentials are
explicitly excluded. Snapshot and release paths are absolute, normalized, bounded, and confined to
their configured roots.

### Upgrade and rollback

`codex-stack-deploy upgrade --release-dir <absolute-release>` performs snapshot, router stop,
immutable release installation, atomic activation, bounded start, and loopback health verification.
A failed start or health check automatically restores the snapshot and previous release.

`codex-stack-deploy rollback --snapshot <id>` is the documented one-command rollback. It stops only
the router, verifies the rollback release, restores configuration and state atomically with their
recorded ownership/modes, activates the previous release, starts the router, and verifies health.
The App Server and codex-web remain independently supervised.

test-environment ordering defect, not a relaxed production permission.

## Residual risks

- Native upgrade/rollback acceptance ran on Ubuntu 24.04 x64. The arm64 release remains
  reproducibly buildable from M5.1, but the M5.3 systemd drill has not run on arm64 hardware.
- Fixture services validate deployment behavior, not a real Codex account or upstream protocol.
- Real-account M0.3, M3.5, and M4.1 switching rows remain unrun by user direction. M5.3 neither
  waives those gates nor claims seamless account continuity or in-flight computation recovery.
