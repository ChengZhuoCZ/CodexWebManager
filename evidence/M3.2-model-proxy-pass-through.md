## Acceptance mapping

### Streaming and non-streaming responses

- `createProxyHandler()` normalizes the request with M3.1 before resolving or opening any upstream.
- Non-streaming request and response bodies pass byte-for-byte with explicit status and safe-header
  forwarding.
- Client authorization, cookies, API keys, account-selection headers, and arbitrary headers are
  not forwarded. Selected-account headers can only come from the internal resolver.
- Upstream `set-cookie` and private response headers are stripped.
- SSE chunks reach the client before the upstream response completes and preserve event order.
- SSE has no aggregate byte ceiling because a valid long-lived stream can be unbounded; memory is
  bounded by stream backpressure and the request has a total deadline.

### Backpressure and cancellation

- Request forwarding pauses the client request when the upstream writable buffer fills and resumes
  it on `drain`.
- HTTP/SSE responses use `pipeline()` so a slow downstream propagates backpressure. The fixture
  sends 16 MiB in 64 KiB chunks and proves both upstream `drain` events and exact byte delivery.
- Destroying an active SSE response destroys the upstream response.
- The exact M0.2-observed WebSocket Responses path uses a raw duplex tunnel. Native `pipe()` provides
  backpressure in both directions, while explicit `end`, `close`, and error handlers terminate the
  opposite socket and release the selected-account lease once.

### Request and response limits

- Declared request bodies above the configured limit receive `413` before upstream resolution.
- Chunked request bodies are counted while forwarded; overflow stops forwarding and receives a
  bounded `413` response.
- Declared non-SSE upstream bodies above the configured limit receive `502` before downstream body
  forwarding. Unknown-length bodies are bounded by a transform.
- Header and total timers bound upstream waiting. All numeric limits are validated and bounded at
  construction.

### WebSocket and network boundary

- The model listener defaults to literal loopback `127.0.0.1:18317` and rejects public, wildcard,
  and hostname binds.
- Only the registered WebSocket route reaches the resolver. Unknown upgrade paths fail before any
  upstream selection.
- Client credentials and compression extensions are stripped from the upstream handshake;
  selected-account headers are injected internally; `set-cookie` is stripped from the 101 response.
- The standalone CLI intentionally does not start this listener yet because composing a production
  resolver requires the M3.3 scheduler/circuit/failover state machine.

## Residual risks

- M3.3 must add bounded account acquisition, retry count, exclusion, backoff, total deadline, and
  the pre-semantic-event failover gate. M3.2 never retries another account.
- If an unknown-length non-SSE response exceeds its limit after response headers were emitted, HTTP
  cannot replace the partial response with JSON; the proxy closes the downstream connection.
- WebSocket compression extensions are deliberately stripped because compressed frame semantics
  are not independently inspected or validated here.
- Auxiliary models/search response compatibility remains M3.4.
- Production composition and graceful process-wide WebSocket shutdown remain later DAG work.
- Real account and cross-account behavior remains deferred. This task provides no evidence of
  seamless conversation continuity and makes no such claim.
