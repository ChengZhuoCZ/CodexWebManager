## Acceptance mapping

### Status, aliases, current route, and events

- `GET /v1/status` returns sanitized router state, `LIMITED_MODE`, the explicit false
  cross-account-E2E flag, active stream count, current route, and account runtime states.
- `GET /v1/accounts` returns aliases and bounded runtime/quota fields without internal IDs.
- `GET /v1/events` returns a bounded SSE replay and live sanitized events with validated numeric
  `Last-Event-ID` cursors.
- Event subscribers are removed after client cancellation and after subscriber callback failure.
- `contracts/router.openapi.yaml` and `contracts/event.schema.json` describe the implemented shapes.

### Separate admin authentication

- The admin authenticator retains only a SHA-256 digest of the configured fixture token and uses
  constant-length digest comparison.
- Only an exact `Authorization: Bearer` value authenticates; model-proxy-style headers are rejected.
- Authenticator string, JSON, and inspection representations are redacted.
- Health and readiness remain public; every M1.3 admin route requires the dedicated credential.

### No secret-bearing response data

- Admin account shapes exclude internal account IDs, `secret_provider`, `credential_ref`, tokens,
  authorization headers, email addresses, and raw upstream payloads.
- Event data passes through structured bounded redaction before storage, replay, or live delivery.
- Strict switch bodies reject unknown fields and never echo rejected input values.
- The contracts have tests preventing credential-bearing response field names from being added.

### Safe LIMITED_MODE switch boundary

- `POST /v1/switch` accepts only the `manual` reason and delegates execution to an injected
  callback; M1.3 itself performs no account access.
- Requests are rejected while an active semantic stream exists.
- Accepted responses, route state, and switch events always say `new_backend_session` and
  `LIMITED_MODE`.
- Request bodies, event backlog, cursors, field values, and HTTP lifecycle timeouts are bounded.

## Residual risks

- Deterministic selection, cooldowns, session stickiness, and real proxy switch execution remain
  M2/M3 work.
- The standalone CLI exposes only health/readiness until M5.2 wires a production admin credential.
- Real cross-account compatibility and continuity remain unverified because this device currently
  has only one Codex account; M0.3 and later approved E2E gates remain deferred, not passed.
