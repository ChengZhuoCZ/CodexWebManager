## Minimal experiment and diagnosis

The initial Tailnet page returned HTTP 200 but rendered the ChatGPT sign-in screen. A sanitized IPC
probe used a newly created bounded browser session and requested only `account/read` plus the legacy
authentication status method without requesting tokens. Before correction, `account/read` returned
no account and said OpenAI authorization was required. No complete response, token, Cookie, account
identifier, email, OAuth callback, or device code was persisted.

A fresh user-authorized device login was completed on the server. Reusing that real credential in
the App Server alone did not change the browser result because codex-web starts a separate App Server
proxy with `/var/lib/codex-web` as its private `CODEX_HOME`.

The isolated positive experiment used a randomly generated, non-provider router marker through
`codex login --with-api-key`. It produced an API-key account object without making an upstream
request. This proved that the browser proxy needed a local authenticated identity while the router
continued to own and inject the real account credential.

## Production result

The deployed topology is now:

- the real authorized ChatGPT credential exists only in the root-owned Primary router credential;
- App Server receives a separate root-owned router-managed marker through its existing systemd
  credential source;
- codex-web keeps the same marker as a regular `0600` file owned by `codex` in its persistent
  `StateDirectory`;
- the App Server and codex-web marker files are equal to each other and different from the real
  router account credential;
- temporary login homes, probes, previous-credential copies, and authorization artifacts were
  removed after verification.

The marker has no OpenAI provider authority. It is valid only with the existing exact loopback
`openai_base_url` because the router removes client authorization and injects the selected real
account credential.

After deployment, the sanitized IPC probe returned an account-present API-key identity. A fresh
browser page did not render the sign-in screen and rendered New task, the composer, and Settings.
After independently restarting `codex-app-server.service` and `codex-web.service`, the same IPC and
fresh-page checks passed again. All three stack services were active and local health returned HTTP
200.

## Residual risk

- A full host reboot was not executed. The marker is in a systemd `StateDirectory`, so it is designed
  to survive a reboot, but M6.6 empirically verifies service restarts and fresh browser sessions only.
- If `openai_base_url` stops pointing to the exact loopback router, both marker files must be removed
  before the services are allowed to start.
- The real router credential can still expire or be revoked and then needs a new user-authorized
  device login.
- Only one real account is configured. Automatic switching and cross-account continuity remain
  untested.
