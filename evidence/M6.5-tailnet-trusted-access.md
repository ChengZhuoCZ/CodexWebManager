# M6.5 explicit Tailnet trusted browser access

## Task record

- Repository: `ChengZhuoCZ/CodexWebManager`
- Branch: `codex/m6-5-tailnet-trusted-access`
- Input commit: `998b1cbd19625471d9a3960a0ec866d9eb556c24`
- Implementation commit: `5b60566dfccb5b4a7555af96434fcb3f31611be4`
- Dependencies: M5.4, M6.1, and G-SECRETS
- Implementation mode: `clean-room`
- Architecture mode: `LIMITED_MODE`

The task adds one opt-in `CODEX_WEB_TRUSTED_TAILNET_ACCESS=1` mode. It is accepted only when
`CODEX_WEB_PUBLIC_ORIGIN` is an exact HTTP origin using an explicit IPv4 address inside
`100.64.0.0/10`. Loopback, hostnames, wildcard origins, HTTPS, and other flag values fail closed.

In trusted mode, codex-web does not load or require the browser access-key file. A top-level HTML
request creates an independent bounded browser session. The session cookie remains `HttpOnly` and
`SameSite=Strict`; unsafe methods still require the session CSRF value, and WebSockets still require
the exact Host, Origin, cookie, and `codex-ipc.v1` subprotocol. Renderer-message filters, workspace
root resolution, and router admin authorization are unchanged. At most 64 trusted browser sessions
are retained. Default and loopback deployments continue to require the site key.

This changes browser access policy only. It does not configure or switch Codex accounts, run a
cross-account test, or claim seamless session continuity.

## Residual risks

- Every Tailnet device allowed by ACL to reach TCP 8214 has high-privilege access to configured
  workspaces. Tailnet membership and ACLs are now the human-access boundary.
- A direct IP HTTP origin cannot set a `Secure` cookie. The Tailnet encrypts the data channel, but a
  future MagicDNS/HTTPS topology requires a separate origin and browser security review.
- Only one real Codex account remains configured. Automatic account switching remains untested.
- M6.2 remains rejected under the user-directed soak-test exception.
